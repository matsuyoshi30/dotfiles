# Concurrency and consistency

What happens when state is shared or interleaved?

- Concurrency — what happens when another transaction, request, async task, or UI event interleaves between read, decide, and write. Whether a conditional UPDATE silently succeeds matching zero rows and execution proceeds as if the update landed
- Isolation level — whether the reasoning holds under the isolation level and database engine actually in use. For example, under PostgreSQL REPEATABLE READ a plain re-read after a row lock does not see rows committed after the snapshot, and a row that does not exist yet cannot be locked, so a pre-check does not stop concurrent creation: that takes a unique constraint whose violation maps to a conflict, or a lock on an existing parent row that every creating path takes. Whether a check-then-insert-or-update could be a single upsert. Whether two transactions that each read and then write different rows can produce write skew
- Lock ordering — whether acquisition order depends on the ordering or grouping of the input. When a bulk operation groups by kind, ordering that flips depending on the request can deadlock. Whether every path that must exclude the others locks the same row; a lock taken by only one side excludes nothing
- Transaction boundaries — whether the boundary sits where existing conventions put it. Whether nesting has nullified an inner isolation-level setting. When a boundary is split, or an external side effect is moved outside it, what users see when only one side succeeds
- Caching — whether some ordering of invalidation and read lets a pre-update value be returned. This includes client-side caches
- Stale responses and stale views — whether a late response to an older request can overwrite the result of a newer one, whether work continues after an `await` once its requester is gone, and whether another action can go through while an asynchronous fill is still pending. When a person reads content and then approves or confirms it, whether the operation carries the version they saw and is rejected if the target changed in between
