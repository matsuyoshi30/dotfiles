# Behavior

Does the changed code do the right thing for every input and state it can meet?

- Correctness — logic errors, null dereferences, inverted conditions, off-by-one
- Edge cases and failure paths — empty collections, division by zero, negative values, unhandled branches, error handling
- Functional impact — whether the change contradicts existing use cases, state transitions, or configuration
- Equivalence claims — when a change says behavior is preserved (swapping an implementation or backend, batching a per-item call, moving a remote call in-process, porting to a new version, extracting a shared helper, recomputing a value on a second path such as a cache or a preview), list what the old path did at its boundaries and check each against the new one: filters and exclusions, the exception types callers branch on, empty and null inputs, which version or revision is selected, whether filtering happens before or after limiting, insert versus upsert semantics, and transport properties (timeouts, size limits, status mapping). For a shared helper, check that every caller still gets its previous output
- Identity and aggregation keys — whether a key used to match, deduplicate, group, sum, or detect changes is unique and stable on both sides, and includes every attribute a downstream consumer distinguishes. Whether two nulls are matched by accident, or values that differ only in representation (decimal scale, whitespace) are treated as different. Whether a derived total follows when its source value changes, and whether a delta is computed and applied against the same population
- Representative values — whether `first`, `firstOrNull`, the first item of a batch, a map keyed so that the last write wins, or a single-valued return collapses a set that can hold several items. Whether a decision is made at a coarser grain (a batch, an invoice, a month) than the unit it applies to while values can differ inside that grain
- Ordering assumptions — whether a function relies on an input order its callers do not guarantee, or a response order the API does not promise. Whether ties are broken the same way everywhere the same rule is applied. Whether splitting and re-joining a list, or moving a sort from the database collation into in-memory comparison, changes the order users see. Whether the sort key is constant or tied across the rows it sorts, leaving the order effectively arbitrary
- Reference date — for data with validity periods and for date-dependent decisions, whether the date used is the one the rule means: today, the date the event occurred, the accounting date, the period being configured, or the date of the record. Whether filtering by today hides rows that were valid at the time being shown or recalculated, and whether something already issued is re-judged by current values
- Guard placement — whether a rule such as "no changes while locked" or "confirm before discarding" is enforced only at one entry point (a disabled menu item, a hidden button, a gate) while other paths reach the same state change: other menus, shortcuts, new modes, bulk operations. Whether the function or model that performs the change enforces it too. Whether a guard whose input loads asynchronously falls to the permissive side while that input is loading or has failed to load
- Silent fallbacks — whether `?: default`, catch-to-null, or return-empty-on-error turns out-of-spec data into a plausible value. Each fallback value needs a specific justification, not "better than crashing"
- Swallowed exceptions — whether the swallowing site retains what a later investigation needs (the exception, the target identifier). Whether the error reaches the user, or the screen just goes blank without telling them. In background work (event handlers, integrations, jobs), whether a swallowed failure or skip reaches someone who will act on it, such as an error tracker or an alert rather than a log line nobody reads. Whether changing how an exception is caught changes retry semantics, such as acknowledging a message the broker would otherwise redeliver, or rethrowing so a permanently failing message is redelivered forever or a non-idempotent handler runs twice
- Intent — whether the code does what the stated intent says it does, completely, and nothing outside it. An unmentioned change belongs in another change or in the description
- Spec gaps — whether an automated process can later overwrite a manual operation. Whether a delete or undo is needed to match a create or update. Whether a no-op guard is needed in certain states
