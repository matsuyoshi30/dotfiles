# Design

Does the change fit the shape of the code around it?

- Identifiers and types — whether identifiers and category values are passed around as raw strings or UUIDs. Whether the representable states are minimal (if there is no need to distinguish absent from empty, collapse them into one). Whether one field, or null, carries a different meaning depending on context or origin (null standing for "called from a particular screen", one id field that holds either an entity id or a revision id), whether fields that only make sense together are kept as independent values, and whether the type can represent a contradictory state (succeeded but no result); a discriminated union or separate fields makes those states unrepresentable
- Naming — whether a name claims exactly what the code does, both for names this change introduces and for existing names whose behavior it alters: the verb (set versus toggle versus delegate), the scope (all versus a filtered subset, a whole category versus one kind of it), and properties of the result (labelled, deduplicated, formatted for display). Whether one concept is called by one word across the change and its siblings, and a word already used nearby for a different concept is not reused. Whether a name is so generic that it cannot be told apart from an existing sibling. Lookup methods encode the lookup key and source (`findByTitle`, `existsByEmail`) rather than vague verbs (`get`, `process`, `check`); names exposed to clients describe what the caller gets or does, not storage mechanics or server-side preconditions
- Invariants — whether they are enforced at construction (constructor, factory, builder) rather than by defensive checks scattered across call sites, and whether an API is more open than the stated intent needs (an overridable method when the goal is unification). When the model is also rebuilt from stored data, moving a check into construction applies it to existing rows too; see Existing data under new rules in the compatibility perspective
- Leftovers — code added with no caller, code this change leaves unreferenced without removing it, commented-out code, a shared utility with a single import site, and defensive code for a condition that can no longer occur
- WHY comments — whether a non-obvious branch says why it exists: a feature-flag path, a migration or double-write state, a recovery path, intentional redundancy
- Comments and documents — whether comments, doc comments, and standalone documents (READMEs, specs shared with other teams, instruction files and skills that agents read) are true when written, not only after a refactor: defaults, dependencies, scope, and claims about libraries or other systems match the code and the versions in use. Whether a comment presents a fact that merely holds today as if it were a rule. Whether the change leaves a document elsewhere in the repository saying something now false, removes an explanation without carrying its information over, or creates a second source of truth. For documents agents act on, whether code samples compile, whether path scoping covers the files the rule is meant for, and whether a summary keeps the exceptions of the full text
- Reuse — whether the same logic already exists somewhere. Whether it is consistent with sibling implementations (other kinds, other screens, sibling modules), and if not, whether there is a reason
- Ripple — whether the same mistake, or the same rewrite, is also needed in other files or for other kinds
- Coupling — what the change makes one part know about another: internal details, shared mutable state, control flags that steer the callee, a whole structure passed where a few fields are used
- Dependency direction — whether an inner or more general part now depends on an outer or more specific one: domain on use case, use case on a database driver's types, an integration layer on the application layer, a shared or design-system package on a feature, a model on how one screen uses it (print-only exclusions, display colors)
- Cohesion — whether what changes together lives together. Whether the change scatters one concept across modules, or packs unrelated responsibilities into one unit

Judge coupling as a balance, not against a fixed target. Do not push every dependency toward the weakest form (passing plain data) by default. Weigh how strong the coupling is against how far apart the two parts live (same module, across modules, across services or teams) and how often they change:

- Strong coupling between parts that live close together and change together is fine, and often clearer than an indirection added to avoid it
- The same strength across a module or service boundary, or toward a part that changes often, is what makes changes ripple
- Loosening coupling has costs too: extra mapping layers, duplicated models, and logic split away from the data it needs. Splitting things that always change together is as much a cohesion problem as lumping together things that do not

Raise a coupling or cohesion finding only when you can name the likely change that would now have to touch both sides, and how far it has to travel. "This could be more decoupled" without that change is not a finding. A dependency-direction finding meets the same bar: name the change on the specific side that would now force an edit on the general side.
